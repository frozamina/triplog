# 途迹 TripLog · 产品需求文档

> **一句话定位**：把一次长途出行拆成「段」，让每一段的时间、花费、等待都可追溯、可对比。

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 产品形态 | 移动端 App（iOS / Android），本地优先存储 |
| 目标用户 | 有高频跨城出行需求的个人用户（学生、异地工作者、销售、探亲） |
| 核心场景 | 单程 100–800km，需 2–4 段交通方式拼接，含多次换乘 |
| 竞品参照 | 记账 App 的颗粒度 × 航旅纵横的行程感 × Strava 的运动记录叙事 |

---

## 1. 背景与问题

现有工具都在解「票」，没有一个在解「一整趟」。

- **12306 / 携程**：只记录你买的那张票，看不见"从家到高铁站"这一段。
- **记账 App**：只知道花了 ¥428，不知道这 428 买来了 6 小时 42 分，其中 1 小时 26 分在等。
- **备忘录**：能写，但算不了。

用户的真实决策困境是：

> 湛江到深圳，我可以坐高铁转地铁（¥428 / 6h42m），也可以坐直达大巴（¥180 / 9h），
> 还可以开车（¥620 油费过路费 / 7h）。
> **我上次选的是哪个？花了多少？下次要不要换？**

这个问题，只有把「整趟」记录成结构化数据才能回答。

### 用户痛点清单

| # | 痛点 | 现状 | 期望 |
|---|---|---|---|
| P1 | 换乘等待是隐形时间黑洞 | 只记得"路上花了很久"，说不清多久在等 | 等待时长独立记录、独立统计 |
| P2 | 多段花费难以归集 | 打车 26 + 高铁 323 + 地铁 5 + 大巴 18，散落各处 | 一趟一个总账，且能拆到每段 |
| P3 | 方案无法复用 | 每次出行重新查一遍路线 | 常用组合存为模板，一键套用 |
| P4 | 无法横向比较 | 凭印象觉得"高铁贵但快" | 同一 OD 的多种组合并列对比 |
| P5 | 特殊情况无处置放 | 晚点 40 分钟、安检排长队、站内迷路 | 每段/每次换乘均可自由备注 + 标签 |

## 2. 核心概念模型

这是整个产品的骨架，务必先理解这三层：

```
Trip（一次出行）  湛江 → 深圳   2026-10-24
  │
  ├── Leg 1      打车   家 → 湛江西站      18min   ¥26
  ├── Transfer 1 换乘等待 站前广场          42min   —
  ├── Leg 2      高铁   G1234 湛江西→深圳北 3h28m  ¥323
  ├── Transfer 2 换乘等待 站内换乘通道      14min   —
  ├── Leg 3      地铁   4号线 深圳北→市民中心 26min  ¥5
  ├── Transfer 3 换乘等待 出站步行          6min    —
  └── Leg 4      步行   市民中心→公司       12min   —
```

**关键设计决策：换乘等待是独立实体，不是 Leg 的一种。**

理由：等待与通行在统计口径上必须彻底分开。只有分开，"你的行程有 22% 的时间在等待"这句话才算得出来。若把等待塞进 Leg，所有时长都会被污染。

### 派生指标（自动计算，不可手填）

| 指标 | 公式 | 意义 |
|---|---|---|
| 总耗时 | 最后一段到达 − 第一段出发 | 门到门真实时长 |
| 通行时长 | Σ Leg.duration | 真正在移动的时间 |
| 等待时长 | Σ Transfer.duration | 真正在等的时间 |
| 等待占比 | 等待时长 / 总耗时 | **产品的灵魂指标** |
| 总花费 | Σ Leg.cost | 不含等待（等待通常不产生费用） |
| 有效时速 | 总里程 / 总耗时 | 含等待的真实速度，远低于票面时速 |
| 每公里成本 | 总花费 / 总里程 | 跨方案比较的统一尺子 |
| 换乘次数 | Transfer 数量 | 折腾程度 |

## 3. 功能范围

### P0 · MVP（本期交付）

1. **创建行程**：出发地 / 目的地 / 日期 / 可选标题
2. **添加段与换乘**：在时间轴上按顺序插入 Leg 或 Transfer，支持拖动排序
3. **分段记录**：方式（步行/公交/地铁/高铁/动车/大巴/驾车/飞机/轮渡/骑行）、起止地点、起止时间、花费、班次座位、备注
4. **换乘记录**：等待地点、时长、等待内容（候车/安检/找路/吃饭/排队打车）、备注
5. **行程详情**：垂直时间轴，段与等待交替呈现，顶部三数概览
6. **行程列表**：按月份分组，卡片摘要（OD、方式链、总耗时、总花费）
7. **基础统计**：本月次数 / 里程 / 花费 / 等待时长 + 时间构成 + 花费构成

### P1 · 增强

8. **路线模板**：把一趟存为模板，下次一键复制再改时间
9. **方案对比**：同一 OD 下的多次记录并列，高亮「最快 / 最省 / 最省心」
10. **实时打卡**：行程进行中点一下开始计时、再点一下结束并自动生成一段（详见 5.3）
11. **标签体系**：晚点、堵车、无座、安检排队、迷路、天气影响，可统计频次
12. **数据导出**：CSV / 图片分享卡片

### P2 · 远期

13. 车票截图 OCR 自动填充
14. 年度出行报告（类似音乐 App 年度总结）
15. 多人同行分摊

### 明确不做

- ❌ 购票、余票查询、改签（这是 OTA 的事，做了就打不过）
- ❌ 实时导航（这是地图 App 的事）
- ❌ 社交、行程分享社区

## 5. 核心流程

### 5.1 记录一趟新行程

```
点「+」新建
  → 填出发地 / 目的地 / 日期        （必填，其余可后补）
  → 加第一段：选方式 → 起点 → 终点 → 出发时间 → 到达时间 → 花费
  → 点「+ 添加换乘」   填等待地点与起止时间（自动从上一段到达时间起算）
  → 点「+ 添加行程段」 继续加下一段（出发时间自动接续上一段等待结束）
  → …… 重复
  → 保存
```

**关键体验约束**：
- 时间默认接续。上一段 10:40 到达，下一段出发时间默认 10:40，用户只需改差值 → 等待时长自动算出。
- 每加一段，底部实时刷新「总耗时 6h42m · ¥428.5 · 换乘 3 次」，让用户边填边看到账。
- 允许先存草稿（status=进行中/草稿），事后补时间与花费。

### 5.2 回看与决策

```
行程列表 → 点开某趟 → 看时间轴
  → 疑问「这趟为什么这么慢？」→ 看时间构成条，等待占 22%
  → 疑问「我到底花了多少？」→ 看花费构成，高铁占 75%
  → 决策「下次试试大巴？」→ 去洞察页看同 OD 方案对比
```

### 5.3 实时打卡（P1 · 行程进行中）

出发时点「开始」，记一个时间戳就开始计时；到站点「结束」，这一段自动成段。

```
点「开始行程」→ 选方式（默认沿用上一段的推测）
  → 计时中，锁屏 / 切后台都不影响（只存 start_at，不跑后台进程）
  → 到站，点「结束本段 › 开始等待」
       ├─ 本段封存：depart_at = start_at，arrive_at = now，时长自动算
       └─ 同时自动开始下一段，类型默认「等待」   ← 关键
  → 等车时什么都不用做，它自己在计时
  → 上车，点「结束等待 › 开始下一段」→ 选方式
  → …… 重复
  → 抵达目的地，点「结束并保存」
```

**「结束即开始」是这套交互的核心。** 换乘的本质就是"一段结束、等待立刻开始"，用户不该思考"我现在点哪个按钮"。一个按钮完成两件事，一趟 5 段的行程从 10 次操作压到 5 次。

**当前段的类型可随时改。** 计时卡下一排 chip：`等待 / 步行 / 打车 / 地铁 / 高铁 / 大巴`。选错了、坐过站了、临时改打车，点一下就切，**已计的时间不清零**。点「等待」时，这一段的归属从 `Leg` 变成 `Transfer`。

**能耗约束（这是它能从 P2 提到 P1 的原因）：**

| 做法 | 结论 |
|---|---|
| 只存 `start_at`，用时是 `now - start_at` 现算 | ✅ 无后台进程、无常驻定时器、不调 GPS |
| `requestAnimationFrame` 刷新，且仅在页面可见时跑 | ✅ 退到后台就停，回来按时间戳重算，不累积误差 |
| 后台定位自动识别到站、自动切段 | ❌ 耗电大且误判率高，明确不做 |

**打卡只管时间，其余后补。** 花费、班次、座位仍是空的。结束行程时提示「还有 3 段没填花费」，可当场补，也可事后进详情页补。

**进行中的行程在列表页置顶**，用左侧赤陶竖条 + 脉冲点标识，点进去就是计时页。

| 字段 | 类型 | 说明 |

| id | uuid | |

| start_at | datetime | |

> **打卡模式下**：用户点「结束本段 › 开始等待」的瞬间，系统以 `after_leg_seq = 当前段` 自动创建一条 Transfer，`start_at = 本段 arrive_at`，`end_at` 留空并在下一次「开始」时写入。用户在计时卡上把类型切到「等待」时，走的也是这条路径 —— 区别只是它由用户主动开始，而不是自动接续。

## 7. 统计与洞察规则

**时间构成条**：通行时长 : 等待时长，两色水平堆叠，全局唯一一处使用强调色。

**方式效率榜**：按方式聚合，列出 总时长 / 总花费 / 平均每公里成本 / 平均时速。

**洞察文案生成**（模板化，不需 AI）：

| 条件 | 文案 |
|---|---|
| 等待占比 > 20% | 「这趟有 1h26m 在等待，相当于从湛江开到茂名的时间」 |
| 单段花费占比 > 70% | 「高铁吃掉了 75% 的预算，但换来了 3h28m 的位移」 |
| 与同 OD 历史最快比，慢 1h 以上 | 「比你的最快记录慢了 1h12m，卡在换乘上」 |
| 每公里成本低于同 OD 均值 | 「这条线你的成本控制得不错，¥0.42/km」 |

## 8. 交互与视觉规范

遵循 `ui-design-system`：Pinterest 审美 · 克制奢华 · 一处焦点。

### 设计 DNA

| 维度 | 决策 |
|---|---|
| 调性 | 安静、理性、有旅行质感。像一本被认真填写的行程手账 |
| 主色 | 墨林绿 `#1D4D3E` — 沉稳、有纵深感，用于主操作与概览卡 |
| 强调色 | 赤陶 `#C4542F` — 只给「花费」和「等待」两个数字用，稀缺才有力 |
| 底色 | 暖纸白 `#F4F2ED`，卡片纯白 `#FFFFFF` |
| 方式色 | 高铁 `#2C5C8F` · 地铁 `#3F7D6B` · 大巴 `#A8763C` · 驾车 `#6A5A8C` · 步行 `#8B8F94` |
| 字体 | 数字/英文 Fraunces（衬线，tabular-nums）；中文标题 Noto Serif SC；正文 Noto Sans SC |
| 圆角 | 卡片 18px · 内元素 12px · chip 999px。三级，不再多 |
| 阴影 | 仅两级：`0 1px 2px rgba(20,23,26,.04)` 与 `0 8px 24px rgba(20,23,26,.07)` |
| 间距 | 8pt 网格 |

### 数据页的例外：表格化

洞察与方案对比这两页承载的是「横向比较」，卡片语言在这里反而失效——圆角、阴影、留白都在阻碍对齐。因此这两页改用**表格 + 仪表盘**结构，但配色 token 完全不动：

| 维度 | 记录类页面（列表 / 详情 / 新建） | 数据类页面（洞察 / 对比） |
|---|---|---|
| 容器 | 圆角卡片 16–18px + 柔和阴影 | 方格拼贴 + 1px 网格线，零阴影 |
| 排布 | 段落呼吸，留白主导 | 指标在左、读数右对齐成列 |
| 数字 | Fraunces 随文排版 | 同字体，固定列宽按列居中 |
| 配色 | 纸白 + 墨绿 + 赤陶 | **完全相同**，不切深色 |

原则：不靠「换皮」区分功能区，两套结构共用同一套 token。用户从详情页跳到洞察页，不应有「进了另一个 App」的断裂感。

### 关键交互

| 场景 | 规范 |
|---|---|
| 卡片 hover | 上浮 2px + 阴影升一级，200ms `cubic-bezier(.2,0,0,1)` |
| 卡片 press | `scale(.985)`，150ms |
| 时间轴节点 | 页面加载时按 60ms 交错淡入上移 |
| 段内展开备注 | `grid-template-rows: 0fr → 1fr`，免测高 |
| 方式选择 chip | 选中时背景填充方式色，文字转白，spring 曲线回弹 |
| 底部实时汇总条 | 数字变化时 `translateY(60%) scale(.8)` 滚入，300ms spring |
| 计时器数字 | `tabular-nums` 等宽，每秒只换数字不换宽度，整行不跳；冒号常亮不闪 |
| 「结束本段」按钮 | 按下 `scale(.97)`；松手后本节从底部淡出上移、新一节淡入，300ms —— 让「一段结束」有物理感 |
| 段类型 chip 切换 | 计时不清零，只换配色与归属；chip 填充色 200ms 交叉淡入 |
| 页面转场 | 详情页从卡片位置 clip-path 圆形扩散（P1） |

### 无障碍底线

- 正文对比度 ≥ 4.5:1，弱化文字仅用于非关键信息且 ≥ 3:1
- 所有点击区 ≥ 44×44px
- 强调色不作为唯一信息载体（等待段同时用虚线 + 图标 + 文案区分）
- 支持 `prefers-reduced-motion`

## 9. 边界与异常

| 场景 | 处理 |
|---|---|
| 跨天行程（夜车） | 日期用 datetime 而非 date，时间轴自动插入「次日」分隔 |
| 用户只记得总时长 | 支持只填起止时间，中间段留空，标记「估算」 |
| 时区变化 | 记录时区偏移，展示按当地时间 |
| 花费为 0（步行） | 正常展示为「免费」，不显示 ¥0 |
| 段之间时间重叠 | 保存时校验并提示，阻断保存 |
| 长时间未结束的行程 | 超过 24h 未完结，标记「待补全」并推送到列表顶部 |
| 打卡忘记点「结束」（在车上睡着了） | 下次打开计时页时，若单段已超 6h，顶部提示「这段已经 8h 12m，是结束了还是还在路上？」——给「按预计到达时间结束」「继续计时」「手动改时间」三个出口，绝不自动结束 |
| 打卡中途杀掉 App / 手机重启 | 时间戳已落本地库，重开即按 `now - start_at` 续上，不丢段 |
| 打卡时坐过站 / 临时改打车 | 直接点对应 chip 改类型，已计时间保留，不中断计时 |
| 打卡结束才发现忘了选方式 | 类型 chip 随时可改，默认按上一段的方式预选 |
| 离线 | 本地优先，全部数据本地存储，云同步为可选增量能力 |

## 10. 成功指标

| 层级 | 指标 | 目标 |
|---|---|---|
| 激活 | 首周完成 ≥ 2 趟完整记录（含换乘） | 60% |
| 留存 | 次月仍有记录行为 | 40% |
| 深度 | 平均每趟记录段数 | ≥ 3 段 |
| 价值兑现 | 模板复用 / 对比页访问占比 | 30% |

**北极星指标：完整记录趟数（含 ≥1 次换乘的行程数）**。只记单段不构成价值，有换乘才有洞察。

## 11. 里程碑

| 阶段 | 范围 | 产出 |
|---|---|---|
| M1 | P0 全部功能 + 本地存储 | 可用的记录工具 |
| M2 | P1 模板 / 对比 / 实时打卡 / 标签 / 导出 | 从记录到决策，且记录成本减半 |
| M3 | P2 OCR / 年度报告 / 同行分摊 | 减少手填，提升回味感 |

> 实时打卡从 P2 提到 P1：它看起来是"锦上添花"，实际上是**唯一能把每趟记录成本从 3 分钟压到 30 秒的功能**，而记录成本直接决定留存。技术上它只是读写一个时间戳，没有后台进程，成本极低。

## 附：三条设计自省

1. **不要在列表页做统计图表。** 列表的任务是「找到那一趟」，不是「看数据」。统计的入口只有一个 Tab。
2. **等待时间是本产品的差异化，视觉上必须让它"扎眼"。** 用虚线、用更浅的底、用赤陶色的时长数字，让它看起来就像浪费掉的时间。
3. **警惕过度结构化。** 用户在路上很累，填 12 个字段会放弃。字段分两层：必填只有方式和时间，其余全部折叠。
